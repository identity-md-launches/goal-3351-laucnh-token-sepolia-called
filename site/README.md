# TEST Staking — Sepolia static site

Plain HTML/CSS/JS, no build step, no CDN dependency. Talks to an injected browser
wallet (e.g. MetaMask) directly via raw JSON-RPC; no runtime library is bundled
because none is needed (ABI calldata is built by hand in `lib.js`).

## Files

- `index.html` — the staking UI (wallet connect, faucet, stake, withdraw, points).
- `styles.css` — responsive, accessible styling.
- `lib.js` — pure logic: exact decimal/base-unit conversion, ABI encode/decode,
  deployment-record validation. Loaded by the browser and also `require()`-able
  from Node for tests, with no DOM or network access.
- `app.js` — wallet/DOM wiring: connects to `window.ethereum`, enforces the
  Sepolia chain, validates the deployment addresses on-chain, and drives the
  faucet / approve+stake / withdraw flows.
- `deployment.json` — runtime data only: `{"chainId":11155111,"token":null,"staking":null}`.
  This is the *only* source of contract addresses. While `token`/`staking` are
  `null` (or fail validation), the page shows "Not deployed yet" and disables
  every contract action. A later wave fills this file in once the token and
  staking contracts are deployed.
- `deploy.html` / `deploy.js` — placeholders reserved for a later assembly wave
  that will deploy the contracts and populate `deployment.json`. They do nothing
  in this item.
- `tests/` — focused, runnable Node tests (see below).

## Serving

No build step. From the `site/` directory:

```
cd site
python3 -m http.server 8080
```

Then open `http://localhost:8080/` in a browser with an injected wallet
extension. Any static file server works equally well (e.g. `npx serve`).

## Running the tests

```
cd site
node tests/run.js
```

This runs:
- `tests/lib.test.js` — pure logic: exact decimal parsing/formatting (no floats),
  deployment-record validation (valid/invalid/missing/null), address validation,
  ABI encode/decode round trips, and selector values cross-checked against
  well-known public 4-byte signatures (`balanceOf`, `approve`, `transfer`,
  `mint`, `stake`, `withdraw`).
- `tests/app.test.js` — integration-style tests of `app.js` against a minimal
  hand-built DOM + `window.ethereum` mock (run through Node's built-in `vm`
  module, no jsdom/no dependency): absent wallet, wrong chain, null/malformed
  `deployment.json`, a fetch failure reading it, a staking contract not bound
  to the configured token, an address with no contract code, account changes,
  insufficient balance/allowance (rejected locally before any transaction is
  sent), an approve-then-stake flow, a user-rejected transaction (code 4001),
  a reverted transaction, and a confirmed withdrawal that refreshes balances.

All mocked wallet/chain data in the tests is confined to `tests/*.test.js` and
clearly constructed there; nothing in the shipped `app.js`/`index.html` invents
balances, addresses, or a deployed status.

## Points rule (shown on the page itself)

One point per second is generated by the pool and split across all stakers in
proportion to their currently active stake. If nobody is staked, that period
earns zero points for everyone. Withdrawing some or all of a stake does not
erase points already earned — it only changes the staker's share of points
earned from that moment forward. `pointsOf(address)` returns a value scaled by
1e18 per whole point (same base-unit convention as the 18-decimal token).

## Faucet

The faucet button calls the token's own open `mint(uint256)` function for the
connected wallet. This is explained on the page: anyone can mint test TEST
tokens to themselves, there is no real value, and this site enforces no limit
beyond whatever the token contract itself enforces.

## Deployment-address validation

Before enabling any action, the page:
1. Loads and validates `deployment.json` (`chainId` must be `11155111`; `token`
   and `staking` must each be `null` or a well-formed `0x` address).
2. Confirms the connected wallet is on Sepolia (chain id `0xaa36a7`), offering
   `wallet_switchEthereumChain` (falling back to `wallet_addEthereumChain`).
3. Checks both configured addresses hold contract code (`eth_getCode`).
4. Calls `token()` on the staking contract and confirms it matches the
   configured token address.

Only once all four checks pass are the faucet/stake/withdraw buttons enabled.
